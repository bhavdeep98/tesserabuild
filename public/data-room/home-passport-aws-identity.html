Tessera / HomePassport only
PROPOSED ARCHITECTURE · 20 SEPTEMBER 2026

A trusted home record starts with verified authority.

Run HomePassport in its own AWS environment. Separate sign-in from home ownership, enforce access on every request, and preserve evidence of what happened.

Cognito answers “who signed in?” HomePassport must answer “what relationship do they have to this home—and what are they allowed to do now?”

Swipe the diagram horizontally to read each block.

Arrows show logical flows, not unrestricted network access. The web edge and Cognito are shown beside the owner for readability but belong to the HomePassport environment. AWS-managed entry services and S3/SQS sit outside the private subnet boundary; Lambda has private VPC connectivity. Kestrel, builder training and builder business databases are outside this design.

01 / Claim the home

Sign in → prove ownership → receive access.

An approved closing attestation and buyer identity evidence create the owner relationship. Scanning the plaque alone reveals no protected record.

02 / Authorize a service

Limit the data → approve the order → track it.

A provider receives only job-specific fields. A separate approval captures plan, price and terms. Ambiguous orders are reconciled, not blindly retried.

03 / Transfer the home

Verify the buyer → replace authority → preserve history.

One transaction invalidates old home grants and establishes the new owner. Eligible home history continues; the seller’s personal information does not automatically transfer.

How the system earns trust

Authority is evidenced.A login or QR scan cannot create ownership. Approved evidence, co-owner rules and recovery review establish the relationship.
Access is enforced.Live permissions, scoped service identities and database policies control each home, field and action. Encryption supports these controls; it does not replace them.
History is attributed.Every assertion names its source. Reported, verified, disputed and corrected are distinct states. A hash cannot prove physical work happened.
Tessera is accountable.Restricted support access, separate security logs, tested recovery and exportable records reduce dependence on operator promises.

The design decisions behind the diagram

Identity layer · person, home and authority are different objects

Person: Cognito user pool for homeowner authentication, MFA and partner federation where appropriate. Map the verified token issuer + subject to an internal principal ID. Do not use email or a phone number as an immutable identity. Provider machine clients have separate credentials and organization membership; a provider’s shared machine identity is not proof of which technician acted.

Home: a stable, opaque Home ID. Address and parcel references can change. QR/NFC is a locator, never a credential. No public API reveals owner identity or history from the locator.

Relationship: store principal_id, home_id, role, evidence_ref, valid_from, valid_to, ownership_epoch in Aurora. Cognito groups and JWT claims must not be the source of current home ownership. Token revocation and permission revocation are separate concerns; application checks close that gap.

Claim: validate an authenticated closing partner’s attestation against the buyer’s identity evidence. Cognito sign-in does not perform title verification or establish legal identity. Select and approve the evidence provider and fallback review process before launch. Require step-up authentication for transfer and sensitive account recovery.

Co-owners and recovery: each owner has an independent verified binding. Proposed policy: all verified owners approve voluntary transfers; disputed cases freeze transfers and new third-party grants while reviewed. Lost phones, seller unavailability, estates and trusts require a documented evidence-and-review path, not support impersonation. Re-linking a recovered account never silently creates new ownership.

Permission layer · live policy before every data release or action

Recommended v1: one versioned policy module shared by the API and worker code, with automated policy tests. Avoid adding a separate policy service until operating needs justify it. IAM protects AWS resources; this application policy protects each home and record.

Evaluate authenticated principal, organization, live relationship, current ownership epoch, agreement route, grant purpose, field classification, action and expiry. Read authority from the writer, not a potentially lagging replica. Default deny; return consistent not-found responses for unbound home lookups. Short-lived login tokens are not a substitute for this check.

The API builds an allowlisted projection, persists disclosure intent, then releases it. Use separate database roles for ownership writes, record access and dispatch. Enforce row-level security with non-owner application roles and trusted transaction-local context; migration roles and bypass privileges stay outside runtime. Reset pooled connection context explicitly and test for cross-request leakage through RDS Proxy.

Transfers lock the home authority row, increment ownership_epoch, close old bindings and write new bindings plus audit/outbox records in one transaction. All earlier-epoch grants, including co-owner grants, stop authorizing new requests. Serialize new release decisions with authority updates; recheck jobs before dispatch. Already delivered bytes and externally accepted orders cannot be recalled.

Owner-initiated service uses the applicable HomePassport/provider agreement route, not a perpetual builder/provider contract. Data-sharing consent is distinct from acceptance of an order’s terms and price. User requests cannot select a different tenant context.

V1 deliberately omits MSK, Redis, OpenSearch, Kubernetes and an always-on chain indexer. They are not required to establish ownership or trust. Add services only for a measured requirement. Application outbox transactions replace the need for Kafka in this workflow.

Audit and proof · protect the evidence without promising the impossible

Commit business audit intent with state changes or before disclosure. A failed durable audit write blocks new protected release. An outbox relay exports minimized events to a separate security account. Monitor the export lag: the interval before independent storage is a real protection gap, not “impossible to rewrite.”

CloudTrail covers AWS operations; it does not automatically record which home fields an application disclosed. Use both infrastructure logs and application audit. Avoid raw documents, tokens and personal field values in logs. Apply S3 Object Lock only to selected audit archives with an approved retention policy, not indiscriminately to personal evidence.

Tessera staff use Identity Center, MFA, temporary role access and an approval record. Sensitive support sessions require a second approver and purpose-bound access. Restrict archive administrators separately from application administrators; alert on deployment, role, key and logging changes. AWS account separation reduces bypass paths; compromise of the organization’s highest administrative privileges remains a residual risk.

Begin with attributed records and reproducible exports. If external verification is required, canonicalize and salt commitments, batch them, publish a root to a selected independent witness and export inclusion receipts with the exact verification material. A witness does not establish truth, completeness or the latest state. An offline export cannot discover events created later.

Retain corrections as linked events and manage personal payload deletion separately. Owners receive an export of eligible content plus an inclusion/redaction manifest. Verify without HomePassport’s API; ongoing hosting, new ownership changes and provider services still require an operator.

Reliability, recovery and the proof required before launch

Availability: two-AZ application connectivity and Aurora writer/reader failover; multi-AZ is not regional disaster recovery. Use point-in-time recovery and separately protected document backups. Scope encrypted cross-region copies against residency policy and recovery needs before claiming regional recovery.

Recovery targets: set RPO and RTO with the pilot customer and demonstrate them with a timed restore. Restore database authority, documents and audit consistently; do not replay revoked grants or resend completed provider jobs. Cognito identity continuity needs its own supported recovery/replication plan—database backups do not back up the sign-in service.

Release evidence: deny a plaque-only claim; deny access to another home; prove that revocation and transfer races block new releases; prevent duplicate provider orders; prove seller personal data is absent after resale; verify an offline export; complete a restore drill. Test stale JWTs, connection-pool context leakage, forged callbacks and privileged-role misuse.

Monitoring: alarm on denied-claim bursts, unexpected permission changes, audit lag, dead-letter messages, unknown job outcomes, failed backups, KMS errors and disabled security logging. Provider outage should pause/reconcile jobs while authorized home history remains usable.

What this changes in the cost document

Do not carry forward $167/month as the price of this architecture. The supplied PDF’s 1,000-home tier lists $118 AWS + $49 managed RPC, but does not separately price the complete identity, API protection, two-instance database, proxy, network, audit and recovery baseline proposed here.

The new cost model should include Cognito users and authentication options; API Gateway/WAF requests; Lambda duration; Aurora writer + reader capacity and I/O; RDS Proxy; S3/KMS; SQS; NAT/endpoints; log retention; backups; and optional proof infrastructure. Include identity-evidence vendors and operating support separately from AWS.

Budget from measured sign-ins, access frequency, document traffic, retention and concurrent jobs—not passport count alone. Removing always-on compute and optional chain dependencies may save cost; added trust controls may increase the fixed baseline. A revised calculator estimate is required before quoting a total.
