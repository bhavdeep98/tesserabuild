Tessera / HomePassport — Data Flow, Encryption & PII Audit

Purpose: state clearly what data comes from where, where it is encrypted, what goes on the ledger, and where we might break a PII rule. Plain English. Based only on the AWS & identity architecture diagram. Assumption per your instruction: the ledger exists.

1. What goes on the ledger (short answer)

Only a hash. Never the data.

  • The ledger receives batched commitments — a single Merkle root per batch,

built from salted SHA-256 hashes of record events.

  • No raw records, no PII, no documents, no addresses, no names ever go on the

ledger. The diagram is explicit: "external ledger receives batched commitments only."

  • A hash proves the record's bytes were not changed. It does not prove the

record is true, complete, or the latest version.

  • The salt/nonce used to build each hash is secret and is not on the

ledger. It travels only inside the owner's authorized export, so the owner can verify offline. Without the salt, nobody can brute-force a known field (e.g. an address) back out of the hash.

On-ledger record = { batch timestamp, Merkle root }. That is all.

4. The data schema — one line each, plain English

Grouped by the three walled stores plus operational objects. Each line: what it is → key fields → PII? → which store.

Ownership & identity

  • Home → one stable opaque home ID + parcel links + lifecycle state + ownership version → not PII → home store.
  • Ownership binding → who is owner/co-owner of a home, with role, evidence reference, valid-from/to, ownership epoch → PII (links a person to a property) → authority store.
  • Principal → internal ID mapped from the Cognito token (issuer + subject) → PII (identity) → personal vault.

Records (home history)

  • Assertion / record event → one fact about the home (e.g. HVAC installed) with source, observed/received time, verification status (reported/verified/disputed/corrected), evidence reference, supersedes-link → mixed: fact is home data, but may embed PII (serials, names) → home history.
  • Home document / evidence file → the actual PDF/photo behind a fact → often PII → S3 (KMS).

Personal

  • Personal vault entry → owner contact, payment, service-account details → PII (sensitive) → personal schema; never auto-transfers at resale.

Consent & services

  • Grant → permission for one provider to receive named fields for one purpose, time-bound, revocable, tied to an agreement version → PII (names fields + recipient) → authority store.
  • Order approval / job → accepted plan/price/terms digest, provider ID, quoted price, idempotency key, job state → PII (links owner to a purchase) → jobs store.

Evidence & accountability

  • Audit event → who did what, when, which fields, policy version, epoch, correlation ID — field names, not raw values → low PII by design (must exclude raw personal values) → Aurora + exported to security account.
  • Outbox event → durable "to be dispatched" record that feeds SQS → minimal PII (digests/IDs) → Aurora.
  • Ledger commitment → batch timestamp + Merkle root → no PII → external ledger.
  • Owner export package → the owner's records + salts + inclusion receipts for offline verification → PII (full record copy) → delivered to owner only.

5. PII audit — where the rules bite

What the design does right (keep these)

  • Ledger holds no PII — only salted, batched hashes. This is the single most

important PII decision and it is correct.

  • Three walled stores — builder / home / personal are separated so a provider

or builder never sees personal data they shouldn't.

  • Encryption everywhere — KMS at rest, TLS in transit, private subnets.
  • Payload built from the grant — a provider only ever receives allowlisted

fields; there is no "filter after the fact" leak.

  • Audit excludes raw personal values — logs record field names, not values.
  • Consent is explicit and revocable — grants name purpose, fields, recipient,

expiry (aligns with purpose-limitation and consent requirements).

Where we could break a rule — open items to close before launch

  1. Right to erasure vs. "append-only" history.

Records are append-only and corrections are linked, not deleted. GDPR/CCPA give a data subject deletion rights. Decide now: personal payloads must be separately deletable (the doc says "manage personal payload deletion separately") even though the home fact stays. Define a retention + deletion schedule per data class. Risk: high if undefined.

  1. Hash of PII can itself be personal data.

Under GDPR, a salted hash of a person's data can still be "pseudonymized personal data," not anonymous — especially if the salt is recoverable. Decide: confirm the salt is never exported to any party who also holds the ledger, and document the hash's legal classification. Risk: medium.

  1. Data delivered to providers cannot be recalled.

Once a provider receives the scoped payload, revocation can't pull it back. Decide: provider agreements (DPAs) must carry retention + deletion obligations, and this must be contractual, not technical. Risk: high without DPAs.

  1. Evidence files are the densest PII (IDs, closing docs).

These sit in S3. Decide: stricter access, shorter retention, and explicit classification for evidence vs. ordinary home documents. Confirm signed URLs (if used) expire fast — access can persist until expiry. Risk: medium.

  1. Data residency / cross-region copies.

The design is single-region (us-east-1). If any owner is in a jurisdiction with residency rules, cross-region backups must be scoped. Decide: residency policy before any cross-region copy. Risk: depends on customer geography.

  1. Ownership binding = a person tied to a physical address.

This is sensitive linkage. Decide: confirm "not found" (not "forbidden") responses for unbound lookups so the API can't be used to confirm who owns a given address. (The design already calls for consistent not-found responses — verify it's enforced.) Risk: medium.

  1. Provider machine identity ≠ which technician acted.

For accountability/audit completeness, a shared provider credential can't prove the individual. Decide: whether per-technician attribution is required for any regulated field. Risk: low–medium.

  1. Privileged admin remains in the threat model.

The doc admits compromise of top AWS org privileges is a residual risk. Decide: dual-control, separated audit-archive admins, and alerting are in place; accept and document the residual risk. Risk: residual, must be documented.

6. One-paragraph summary for the auditor

Data enters HomePassport from three sources only — builders/closing partners (approved facts + ownership evidence), owners (identity, consent, uploads), and providers (job results) — all through WAF + API Gateway. It is stored in Aurora (KMS) and S3 (SSE-KMS), split into builder / home / personal stores, and moves over TLS at the edge and private VPC paths internally. The ledger only ever receives salted, batched hashes — no PII, no documents. The main compliance work before launch is not encryption (that is handled) but lifecycle: defining per-class retention and deletion (right to erasure against append-only history), classifying the salted hash legally, and binding providers to retention/deletion obligations by contract since delivered data can't be recalled. ```
